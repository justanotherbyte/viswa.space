Let's put the program counter and the memories together to begin processing our instruction. We'll use the same instruction as the book: `lw x6, -4(x9)`, or `111111111100 01001 010 00110 0000011` as binary.

<Side caption="lw is an I-type instruction. Reading right to left: op says it is a load, rd is the destination x6, funct3 = 010 picks a 32-bit word, rs1 is the base register x9, and imm is the 12-bit signed offset -4.">
  <InstrFields />
</Side>

What does this instruction do? It loads a 32-bit word at address `x9 + (-4)` from memory into `x6`. Let's think about what operations we'll need.

0. Read instruction from instruction memory. This address will come from the program counter (PC).
0. Extract the destination and source registers.
0. Compute the address using the offset `imm`ediate and the source registerr `rs1`.
0. Read the value at said address.
0. Store the data at said adress into the destination address `rd`.
0. Increment program counter (by `+4`).

We don't have hardware to complete some of these steps yet (notably an ALU), but let's wire together the memories as much as we can so far.

```verilog
module riscv(
  input logic clk
);
  logic [31:0] pc_next, pc, instr;
  logic reg_file_WE = 1;

  program_counter prog_counter ( .pc_next(pc_next), .pc(pc), .clk(clk) );
  ins_mem ins_mem ( .A(pc), .RD(instr) );
  reg_file reg_file( .A1(instr[19:15]), .clk(clk), .WE3(reg_file_WE) );

endmodule
```

> [!NOTE]
> I've called this module riscv, but note this is really just the data path so far.

Let's trace through this with a CocoTB test bench.

```python
async def load_program(dut, instructions: list[int], start: int = 0x0):
  for i, instr in enumerate(instructions, start=start):
    dut.ins_mem.mem[i].value = instr
    await Timer(1, unit="ns")

@cocotb.test
async def test_instruction_flow(dut):
  await load_program(dut, [0xFFC4A303], start=0x1)
  dut.pc_next.value = 0x4
  dut.reg_file.mem[0x9].value = 0x2004

  cocotb.start_soon(Clock(dut.clk, 10, unit="ns").start())

  assert dut.prog_counter.pc.value == 0x0
  assert dut.reg_file.A1.value == 0x0
  assert dut.reg_file.RD1.value == 0x0

  await RisingEdge(dut.clk)
  await Timer(1, unit="ns")

  assert dut.reg_file.RD1.value == 0x2004
```

My `load_program` function is quite simple. But there's a few interesting points to talk about here in regards to byte and word addressing. I'm initially loading one instruction into the
instruction memory at word address `0x1`. We set `pc_next == 0x4` because the instruction memory is [byte addressed](/projects/zero-to-riscv/single-cycle/instruction-memory) when being read.

I've loaded an arbitrary value of `0x2004` into the `x9` register simply because it matches the arbitrary value in the book. Any 32-bit value would work here - I simply want to prove that a value is indeed being loaded from our `x9` register, i.e the `rs1` field in my instruction.

The three asserts exist just to convince myself prove that the obvious is true. Before any clock cycle completes, the program counter would still output `0x0` (`pc_next` hasn't propagated to `pc` yet), and hence
the instruction memory would still be combinationally reading from address `0x0`. The latter two asserts are just tracing along from this initial condition.

We wait for a rising edge of the clock. We expect the hardware to load the 32-bit address stored in the register `x9` which is what happens!

Logically, the next-step is to take this address and compute the actual address we need with our offset. For this, we'll need an Arithmetic Logic Unit (ALU), which we'll cover next.
