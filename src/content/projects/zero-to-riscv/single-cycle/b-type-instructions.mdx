Adding support to our data path for B-type instructions doesn't require too many changes. Let's think about this logically. We know we'll need to control what value `pc_next` becomes instead of the normal `+4`, so we'll introduce a `pc_src` control signal.

Something I've begun to do more of, is look at the official RISC-V documentation.

<ZoomImage src={bTypeFormat} alt="caption=B-type instruction format from the official RISC-V spec." />

One thing I noticed is how broken up the `imm` value is in the instruction bits. In B-type instructions, the immediate is 13-bits long. Looking at the RISC-V spec above, we can see that:

- Bit 12 is at `instr[31]`
- Bit 11 is at `instr[7]`
- Bits 10:5 are at `instr[30:25]`
- Bits 4:1 are at `instr[11:8]`

Why no `imm[0]` bit? Well, for B-type instructions, their offset is always even, which means `imm[0]` always equals 0, so it'd be a waste to store it in the instruction itself.

# Handling B-type immediate values

This immediate format doesn't match any of the previous formats that we encountered. So we'll need to update our `extend` block. We now have 3 possible cases, one for I/S/B instruction types. So we need to add an additional bit
to our `imm_src` control signal.

```verilog
module extend (
  input logic [31:7] imm,
  input logic [1:0] imm_src,
  output logic [31:0] imm_ext
);

  always_comb begin : mux_imm_ext 
    case (imm_src)
      2'b00: imm_ext = { {20{imm[31]}}, imm[31:20] }; // I-type
      2'b01: imm_ext = { {20{imm[31]}}, imm[31:25], imm[11:7] }; // S-type
      2'b10: imm_ext = { {20{imm[31]}}, imm[7], imm[30:25], imm[11:8], 1'b0 }; // B-type
      default: imm_ext = 'x; // don't care
    endcase
  end

endmodule
```

Let's look at the additions made to our `instruction_flow` test here. After the `or` instruction finishes, we need to now emulate a control unit to adjust our control signals for our branch instruction:

- Branch instructions need to set the next PC address, and they do this via `pc_target`, which is multiplexed and controlled by setting `pc_src = 1`.
- `beq` checks to see if both values in the two source registers are equal. It does this by performing a subtraction with the ALU and checking if the result is 0, hence, we set `alu_ctrl = 001`.
- We set `alu_src = 0` because `beq` checks two *registers* for equality, hence, setting it to 0 chooses `reg_file.RD2` to read from rather than the immediate value.
- B-type instructions need `imm_src = 10` to extract its immediate value.

I've set our `beq` instruction to jump by `+8` if `x0 == x0` which is obviously true! Hence, we skip the `addi x4, x0, 42` instruction and jump straight to the `addi x2, x0, 3`. Why 8? This should be self-explanatory by now, but remember the instruction memory byte addressed not word-addressed. Adding 8 bytes means we skip forward two words, hence two instructions.

My test checks to see if `x4` holds 42 or not and if the value changed at all. If the value hasn't changed and it doesn't store 42, we know that the `beq` instruction successfully executed.

We also write some additional logic to see if the final instruction executed, i.e, does `x2 = 0 + 3 = 3`.
