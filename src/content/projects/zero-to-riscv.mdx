# Single-cycle processor

We begin by piecing together a single-cycle processor, i.e, a processor where a single instruction takes one clock cycle to execute. We'll start by defining some of the memories we'll need: instruction memory, a 32x32 register file and data memory. Oh, and we'll discuss the program counter here too.

## Program Counter

A good place to start is the program counter. We'll cover how RISC-V addressing works here. We'll start off with the storage element of the program counter here, and expand the PC to its complete form later on.

This is pretty simple. We want our program counter to give us a new address every clock cycle, and we want a way to control the next instruction address (we're not necessarily always incrementing by +4, jumps etc can override this).

This behaviour can be modelled incredibly simply (and flexibly) with a D-Flip-Flop (DFF) as so:

<SideBySide>
<Side caption="The program counter: a 32-bit D flip-flop that latches pc_next on every rising clock edge.">

```verilog
module program_counter(
  input logic clk,
  input logic [31:0] pc_next,
  output logic [31:0] pc
);

  always_ff @( posedge clk ) begin
    pc <= pc_next;
  end

endmodule
```

</Side>
<Side caption="Its cocotb test. Drive pc_next, wait one rising edge, then check pc took the value.">

```python
@cocotb.test
async def test_pc_dff(dut):
    instruction = 0xFFC4A303 # lw x6 -4(x9)
    cocotb.start_soon(
      Clock(dut.clk, 10, unit="ns").start()
    )

    dut.pc_next.value = instruction

    await RisingEdge(dut.clk)
    await Timer(1, unit="ns")

    assert dut.pc.value == instruction
```

</Side>
</SideBySide>

We'll expand this later to include incrementing with an ALU/specifying a specific instruction to jump to.

I mentioned earlier that the PC increments by `+4`. Why? Those who've studied computer architecture before will know the program counter stores the address of the instruction currently being executed (we'll take `pc` to be the "stored" port here).
So, why not `+1`? This comes down to how RISC-V is addressed.

RISC-V is byte-addressed rather than word-addressed. This is the case for most modern ISAs as far as I'm aware. Being byte-addressed has many benefits in the modern world that I won't
go into too much detail here about, but a few to take note of: the ISA itself has granular load and store instructions such as `lb` and `sb` so it helps to address to bytes rather than full 32-bit
words. A lot of languages today also assume a byte-addressed model - like C for example: `sizeof(char) = 1 byte`.

Being byte-addressed means to get the next address, simply incrementing by `+1` won't get us our next instruction. We'll need to increment by 32-bits, or 4 bytes, hence the `+4`.

## Instruction Memory

The instruction memory is purely combinational - it combinationally reads a 32-bit instruction at address `A` onto the read data output `RD`. Let's look at how we might implement this. First, defining our ports and some memory:

<SideBySide>
<Side caption="ins_mem: 64 words of 32 bits, read combinationally at A.">

```verilog
module ins_mem (
  input logic [31:0] A,
  output logic [31:0] RD
);

  logic [31:0] mem [0:63];

  assign RD = mem[A[7:2]];

endmodule
```

</Side>
<Side caption="The same mem array. Each row is one word of four bytes, and A points at the word's lowest byte (blue).">
  <MemArray />
</Side>
</SideBySide>

> [!NOTE]
> The keen-eyed reader will notice something interesting. A 32-bit address implies $2^{32}$ possible 32-bit words of instruction memory. This is gigabytes of instruction memory, and is obviously absurd,
> hence, we restrict our `mem` array to simply 64 (`[0:63]`) words of 32-bit (`[31:0]`) instructions. $2^{32}$ is simply the upper-bound of what RISC-V could theoretically support.

RISC-V being byte-addressed means that address `A` doesn't point to a full 32-bit instruction word. So... what does it point to? and how do we access our entire instruction?

Let's look at some examples first.

- `A = 0x0` - Ok this seems pretty easy. We simply drive `RD` to `mem[0]`.
- `A = 0x4` - Erm. Woah, we just skipped 3 instructions?
- `A = 0x8` - Okay. Now I'm confused!

Like I said before, the address `A` here actually points to the lowest-significant byte of our instruction. If we simply used `A` is the address in `mem`, we'd miss out many instructions.

<SideBySide reverse>
<div>

If you haven't noticed, we can effectively get the right "row" in `mem` by simply dividing `A` by 4, i.e `instruction = mem[A/4]`. Cool we have a rule to follow, but how does this translate to hardware?
Simple! Remember that shifting right is effectively a division by 2! So we just shift `A` to the right by 2 bits.

`A` shifted right gives us `A[31:2]`, but our `mem` size is just 64 words, so we'll keep only the bottom 6 bits ($2^6 = 64$), hence `A[7:2]`.

</div>
<Side caption="Shifting A = 0x08 right. Each shift moves every bit one place, so the value halves: two shifts divide by 4 and land on mem[2].">

</Side>
</SideBySide>

## Register File

The register file holds the 32 RISC-V registers (`x0`-`x31`). The input addresses `A1`, `A2` and `A3` are all 5-bits wide. The register file here isn't byte-addressed, rather the addresses correspond to the respective register numbers.

<SideBySide>
<Side caption="The register file: two combinational read ports (A1, A2) and one write port (A3) that writes WD3 on the rising clock edge when WE3 is high.">

```verilog
module reg_file(
  input logic [4:0] A1, A2, A3,
  input logic [31:0] WD3,
  input logic clk, WE3,
  output logic [31:0] RD1, RD2
);

  logic [31:0] mem [0:31];

  assign RD1 = mem[A1];
  assign RD2 = mem[A2];

  always_ff @( posedge clk ) begin : write_A3
    if (WE3) begin
      mem[A3] <= WD3;
    end
  end

endmodule
```

</Side>
<Side caption="Its cocotb test. Write 0x8 to x7 and 0xA to x8, then read both back through RD1 and RD2.">

```python
async def write_to_address(dut, address: int, value: int):
  dut.WE3.value = 1
  dut.WD3.value = value
  dut.A3.value = address
  await RisingEdge(dut.clk)
  await Timer(1, unit="ns")
  dut.WE3.value = 0

@cocotb.test
async def test_read_write(dut):
  cocotb.start_soon(Clock(dut.clk, 10, unit="ns").start())

  await write_to_address(dut, 0x7, 0x8)
  await write_to_address(dut, 0x8, 0xA)

  dut.A1.value = 0x7
  dut.A2.value = 0x8
  await Timer(1, unit="ns")

  assert dut.RD1.value == 0x8
  assert dut.RD2.value == 0xA
```

</Side>
</SideBySide>

One thing I'd like to point out is the constant register `x0` which is always always `0`. We could wire `mem[0] = 0` and change our sequential condition to `WE3 && A3 != 0` but to save on flops during synthesis we can simply reduce our memory size like so:
<SideBySide>

```verilog
module reg_file(
  input logic [4:0] A1, A2, A3,
  input logic [31:0] WD3,
  input logic clk, WE3,
  output logic [31:0] RD1, RD2
);

  logic [31:0] mem [1:31];

  assign RD1 = A1 != 0 ? mem[A1] : '0;
  assign RD2 = A2 != 0 ? mem[A2] : '0;

  always_ff @( posedge clk ) begin : write_A3
    if (WE3 && A3 != 0) begin
      mem[A3] <= WD3;
    end
  end

endmodule
```

<Side caption="We add additional test logic here - we attempt to write some dummy value 0xF to x0 and we ensure that x0 remains 0">

## Data Memory

The data memory is implemented similarly to the Instruction Memory, except it has the ability to write to it too. In a real RISC-V architecture, the instruction memory should also be writeable (otherwise how else do you expect to flash/load instructions?).

<SideBySide>

<Side caption="This is incredibly similar to our instruction memory, except we include writing logic.">

```verilog
module data_mem(
  input logic clk, WE,
  input logic [31:0] A,
  input logic [31:0] WD,
  output logic [31:0] RD
);

  logic [31:0] mem [0:63];

  assign RD = mem[A[7:2]];

  always_ff @( posedge clk ) begin
    if (WE) begin
      mem[A[7:2]] <= WD;
    end
  end

endmodule
```

</Side>

<Side caption="We write 3 dummy values to 3 arbitrary addresses and we ensure the values are written by reading from the same addresses.">
```python
async def write_to_address(dut, address: int, value: int):
  dut.WE.value = 1
  dut.A.value = address
  dut.WD.value = value
  await RisingEdge(dut.clk)
  await Timer(1, unit="ns")

  dut.WE.value = 0

async def read_from_address(dut, address: int) -> int:
  dut.WE.value = 0
  dut.A.value = address
  await Timer(1, unit="ns")

  return dut.RD.value

@cocotb.test
async def test_read_write(dut):
  cocotb.start_soon(Clock(dut.clk, 10, unit="ns").start())

  await write_to_address(dut, 0x7, 0x8)
  await write_to_address(dut, 0x8, 0xA)
  await write_to_address(dut, 0x0, 0xF)

  assert await read_from_address(dut, 0x0) == 0xF
  assert await read_from_address(dut, 0x7) == 0x8
  assert await read_from_address(dut, 0x8) == 0xA
  ```

## Putting the memories together

Let's put the program counter and the memories together to begin processing our instruction. We'll use the same instruction as the book: `lw x6, -4(x9)`, or `111111111100 01001 010 00110 0000011` as binary.

<Side caption="lw is an I-type instruction. Reading right to left: op says it is a load, rd is the destination x6, funct3 = 010 picks a 32-bit word, rs1 is the base register x9, and imm is the 12-bit signed offset -4.">
  <InstrFields />
</Side>

What does this instruction do? It loads a 32-bit word at address `x9 + (-4)` into `x6`. Let's think about what operations we'll need.

0. Read instruction from instruction memory. This address will come from the program counter (PC).
0. Extract the destination and source registers.
0. Compute the address using the offset `imm`ediate and the source registerr `rs1`.
0. Read the value at said address.
0. Store the data at said adress into the destination address `rd`.
0. Increment program counter (by `+4`).

We don't have hardware to complete some of these steps yet (notably an ALU), but let's wire together the memories as much as we can so far.

```verilog
module riscv(
  input logic clk
);
  logic [31:0] pc_next, pc, instr;
  logic reg_file_WE = 1;

  program_counter prog_counter ( .pc_next(pc_next), .pc(pc), .clk(clk) );
  ins_mem ins_mem ( .A(pc), .RD(instr) );
  reg_file reg_file( .A1(instr[19:15]), .clk(clk), .WE3(reg_file_WE) );

endmodule
```
